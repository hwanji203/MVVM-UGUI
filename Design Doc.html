MVVM UGUI

팀 공용 가이드

기준 버전 v0.4.0최종 갱신 2026-10-22

UGUI 화면을 ViewModel · View · Element로 나눠, 화면마다 반복되던 연결 코드를 줄이는 패키지. 값은 Bindable에 담고, 재사용 위젯(Element)이 그 값을 구독해 스스로 따라간다. 화면을 열고 닫는 일은 ScreenManager가 맡는다.

01 / OVERVIEW

개요

ViewModel

화면 하나의 상태(Bindable)와 입력(Command). 순수 C#이고 View·Element를 모른다.

View

프리팹 루트의 MonoBehaviour. Element를 필드로 들고 Bind에서 ViewModel과 잇는다.

Element

재사용 위젯 41종. 한 타입의 값을 보여주거나 입력을 받는다.

화면마다 직접 쓰는 것은 ViewModel 하나 + View 하나 + 프리팹이다. 자식 찾기, GetComponent, 위젯 AddListener, "값이 바뀌었으니 이것·저것 갱신" 호출은 쓰지 않는다. 값이 바뀌면 그 값에 묶인 Element가 따라간다.

참조는 View → ViewModel → Model 한 방향이다. Model(게임 데이터·설정 SO·이벤트)은 프로젝트의 것이고, 패키지는 특정 이벤트·사운드 시스템을 모른다. 프로젝트와 잇는 곳은 클릭 소리와 화면 열기 요청 두 군데이며 둘 다 선택이다(05 연결점).

왜 만들었나

예전 MVP 방식은 리플렉션과 형변환으로 반복 작업을 줄였다. 반복은 줄었지만 성능에 문제가 있었고, 값을 쓸 때마다 형변환을 해야 했다.

그래서 제네릭을 바탕으로, UI Toolkit의 Binding처럼 코드 한 줄로 UI와 Bindable을 묶는 방식으로 만들었다. UI에서 자주 쓰는 기능은 Element로 잘게 나눴다 — 값을 받아 TMP에 적용하는 TextViewElement, 눌리면 묶인 동작(Command의 Action)을 실행하는 ButtonElement 등. 필요한 Element를 Bindable과 연결하는 것만으로 반복 작업이 줄어든다.

02 / QUICK START

빠른 시작

  1. 씬 준비

    루트 Canvas(Screen Space - Overlay, CanvasScaler) 오브젝트를 씬 최상위에 두고 ScreenManager를 붙인다. 매니저는 Awake에서 같은 오브젝트의 Canvas를 잡고 DontDestroyOnLoad로 씬을 넘어 산다. 클릭을 받으려면 EventSystem도 씬을 넘어 하나 있어야 한다.

  2. ViewModel 작성

    AbstractViewModel(팝업은 AbstractPopupVM)을 상속한다. 상태는 get-only Bindable<T> 속성, 버튼은 Command로 둔다. 여는 쪽이 넣을 값은 Setup(...) 메서드로 받고, ResetForOpen()에서 그 값을 되돌린다.

  3. View 작성

    ScreenView<TVM>(팝업은 AbstractPopupView<TVM>)를 상속하고 Element를 [SerializeField] 필드로 둔다. Bind(TVM vm)에 element.Bind(vm.값)을 한 줄씩 쓴다.

  4. 프리팹 만들기

    루트에 View · Canvas(중첩) · GraphicRaycaster, 자식에 Element 컴포넌트를 붙인다. 루트 GameObject 인스펙터 머리의 MVVM UGUI · Element 이름으로 채우기를 누르면 빈 필드가 같은 이름의 자식으로 채워진다. 루트는 켠 채로 저장한다.

  5. 매니저에 등록

    ScreenManager의 Screen View Prefabs 목록에 프리팹을 넣는다. ViewModel 타입 하나에 프리팹 하나다.

  6. 열기 · 닫기

    screenManager.Open<TVM>(vm => vm.Setup(...))으로 연다. 닫기는 Close<TVM>(), 팝업은 ViewModel이 RequestClose()를 부른다.

예제 A · 팝업 하나 만들기 (ViewModel + View + 프리팹) 
using System;
using MVVM.UGUI.Binding;
using MVVM.UGUI.Templates.Popup;

namespace Example
{
    public class RewardPopupVM : AbstractPopupVM
    {
        public Bindable<string> Title { get; } = new();
        public Bindable<int> Gold { get; } = new();
        public Command ClaimCmd { get; }

        private Action _onClaim;

        public RewardPopupVM() => ClaimCmd = new Command(Claim);

        // 여는 쪽: screenManager.Open<RewardPopupVM>(vm => vm.Setup("보상", 120, OnClaim));
        public void Setup(string title, int gold, Action onClaim)
        {
            Title.Value = title;
            Gold.Value = gold;
            _onClaim = onClaim;
        }

        private void Claim()
        {
            _onClaim?.Invoke();
            RequestClose();              // 닫을지는 ViewModel이 정한다
        }

        protected override void ResetForOpen()
        {
            base.ResetForOpen();         // CloseCmd 되돌리기
            ResetAll(Title, Gold, ClaimCmd);
            _onClaim = null;
        }
    }
}
using MVVM.UGUI.Elements.Commands;
using MVVM.UGUI.Elements.Display.Texts;
using MVVM.UGUI.Templates.Popup;
using UnityEngine;

namespace Example
{
    public class RewardPopupView : AbstractPopupView<RewardPopupVM>
    {
        [SerializeField] private TextViewElement titleText;
        [SerializeField] private NumberTextElement goldText;
        [SerializeField] private ButtonElement claimButton;

        protected override void Bind(RewardPopupVM vm)
        {
            base.Bind(vm);               // 닫기 요청 · 닫기 버튼 · 배경 연결
            titleText.Bind(vm.Title);
            goldText.Bind(vm.Gold);      // int 오버로드
            claimButton.Bind(vm.ClaimCmd);
        }
    }
}

03 / BINDING & VIEWMODEL

바인딩과 ViewModel

ViewModel은 값을 Bindable에 담고, Element는 그것을 구독한다. 구독하는 길은 Bind 하나이고, 구독하는 순간 현재 값을 한 번 받는다. 그래서 화면을 처음 열 때 "전부 갱신"을 따로 부르지 않는다.

public Bindable<int> Gold { get; } = new(0);            // 원본 상태 — get-only
public IReadOnlyBindable<string> GoldText { get; }      // 파생 값 — 읽기 전용으로 노출
public Command BuyCmd { get; } = new();                 // 버튼

public ShopVM()
{
    GoldText = Bindable.Select(Gold, g => $"{g:N0} G");   // Gold가 바뀌면 같이 바뀐다
}
API결과와 주의점
Bindable<T>(T initial = default)초기값은 생성자로 준다. Reset()은 이 값으로 돌아간다. 객체 초기화({ Value = 5 })는 생성 뒤 대입이라 초기값이 아니다.
Value같은 값(EqualityComparer<T>.Default)이면 무시하고, 다르면 구독자 전부를 부른다. 참조 타입의 내부만 바뀌면 알 수 없다 — 새 값을 넣거나 BindableList를 쓴다.
Bind(Action<T>) → IDisposable구독 즉시 현재 값으로 한 번 부른다. 돌려받은 핸들을 Dispose하면 끊긴다.
Bindable.Select(a, f)
Bindable.Combine(a, b, f)		파생 값. IReadOnlyBindable<TR>이면서 IDisposable이다. 원본이 ViewModel보다 오래 살면 Own으로 맡긴다. 원본은 1개·2개까지 받는다.
Command(Action = null, bool active = true)Execute()는 꺼졌거나 동작이 없으면 무시한다. Action 속성으로 동작을 갈아 끼우고, SetEnabled(bool)로 잠근다. 버튼은 Active를 구독해 잠김을 그린다. Reset()은 생성자의 동작·켜짐으로 돌아간다.
Command<T>같은 모양에 Execute(T). 실행할 때 인자가 필요한 입력(끌어다 놓은 곳 번호 등).
Signal<T>Fire(T)마다 알린다. 값을 저장하지 않아 같은 값도 매번 알리고, Bind 할 때는 부르지 않는다. 토스트·데미지 숫자 같은 사건용.
BindableList<T>Add·Remove·RemoveAt·Clear는 목록 전체를 알리고, 인덱서 대입은 그 칸만 알린다. Reset()은 비어 있지 않을 때만 비운다.
AbstractViewModelOwn(IDisposable)은 Dispose 때 함께 푼다. ResetForOpen()(abstract)은 매니저가 열 때마다 setup 직전에 부른다. ResetAll(params IResettable[])로 한 줄에 되돌린다.
IInitializable.Initialize()선택. View의 Awake에서 Bind 전에 한 번 불린다. 직렬화 필드(SO)를 쓰는 구독·파생 값은 여기서 만든다.
DisposableBag해제 핸들 여러 개를 담았다가 Clear()로 한 번에 푼다. 프로젝트 쪽 구독 정리에도 쓸 수 있다.

  • 넣지 않는 것: Model이 채우는 값(다시 열면 Model이 바뀔 때까지 기본값이 보인다), 양방향으로 저장되는 값(되돌린 값이 저장으로 흘러간다), 한 번만 할 일(직렬화된 SO 구독·Own·파생 값 — Initialize에 둔다. 여기 두면 열 때마다 쌓인다).
  • 바인딩 객체를 새로 만들지 않는다. View는 Awake에서 묶은 객체를 계속 든다. get-only 속성이면 다시 대입할 때 컴파일 오류(CS0200)로 막힌다.
  • 파생 값은 IResettable이 아니라 넘기면 컴파일 오류다. 원본을 되돌리면 따라온다.
  • setup으로 받은 대상을 구독했다면 여기서(그리고 Dispose에서) 구독을 풀고, 다음 Setup에서 다시 구독한다(HUD 예제). 되돌릴 것이 없으면 빈 override를 둔다.
04 / VIEW & ELEMENT

View와 Element

View는 ScreenView<TVM>를 상속한다. ViewModel은 View의 직렬화 필드 [SerializeField] internal T viewModel = new T()로 만들어진다. ViewModel에 [Serializable]을 붙이면 View 인스펙터 아래에 ViewModel의 필드가 보여 SO를 끌어다 놓을 수 있고, 붙이지 않으면 new T() 그대로다. Bindable은 직렬화되지 않아 상태가 프리팹에 섞이지 않는다.

View가 파괴될 때(OnDestroy) ViewModel을 Dispose한다. View에는 연결 목록이 없다 — Element가 자기 연결을 들고, 다시 Bind 하면 이전 연결을 끊고, 파괴될 때 스스로 푼다. 직접 끊을 때는 Unbind().

[Serializable]
public class SettingsVM : AbstractViewModel, IInitializable
{
    [SerializeField] private SettingsSO settings;          // ViewModel이 SO를 직접 직렬화한다
    public Bindable<float> Volume { get; } = new();

    public void Initialize() { /* settings 구독 — 생성자에서는 아직 null */ }
    protected override void ResetForOpen() { }
}

public class SettingsView : ScreenView<SettingsVM>
{
    [SerializeField] private SliderElement volumeSlider;

    protected override void Bind(SettingsVM vm) => volumeSlider.Bind(vm.Volume);
}

이름으로 채우기

  • View가 붙은 GameObject 인스펙터 머리의 MVVM UGUI · Element 이름으로 채우기 버튼, 또는 Tools → MVVM UGUI → 선택한 View 의 Element 이름으로 채우기.
  • 비어 있는 Element 필드만, 같은 이름의 자식(꺼진 것·깊은 것 포함)으로 채운다. 이미 넣은 참조는 그대로 둔다. Undo 된다.
  • 이름은 앞의 m_를 떼고 글자·숫자만 소문자로 비교한다(hpText ↔ HP Text ↔ Hp_Text). 그 자식에 필드 타입의 컴포넌트가 있어야 한다.
  • 같은 이름이 둘 이상이거나 못 찾으면 비워 두고 콘솔에 경고한다 — 인스펙터에서 끌어다 놓으면 된다.
  • 안쪽에 다른 View(ScreenView·ItemView)가 붙은 오브젝트는 그 아래까지 그 View의 것이라 찾지 않는다. 부모 클래스의 private 필드도 채운다.
  • 비워 둬도 되는 필드에는 [Nullable]을 붙인다. 인스펙터에서 이름이 기울임꼴로 보이는 표시일 뿐이므로 쓰는 쪽에서 closeButton?.Bind(...)로 확인한다.

05 / SCREENS

화면 열기·닫기

모든 화면은 매니저로 연다. 팝업뿐 아니라 HUD처럼 계속 떠 있는 화면도 시작을 맡은 컴포넌트가 Open으로 연다(HUD 예제). 여는 쪽은 View를 모르고 ViewModel 타입만 안다. 그때마다 넣을 값은 setup에서 ViewModel의 Setup(...)으로 넣는다. 매니저는 ViewModel을 돌려주지 않는다 — 닫힌 뒤 재사용된 ViewModel에 값을 넣는 실수를 막는다. 열린 동안 바뀌는 값은 ViewModel이 Model을 구독한다.

API결과와 주의점
Open<TVM>(Action<TVM> setup = null)OpenAsync(setup).Forget(). TVM : AbstractViewModel, new().
OpenAsync<TVM>(setup)쉬는(열려 있지 않은 — 꺼졌거나 닫기 연출 중인) 인스턴스를 고르거나 새로 만들고 → 맨 위로 → ResetForOpen → setup(vm) → 열기 연출까지 기다린다. 프리팹이 없으면 오류 로그만 남긴다.
Close<TVM>() · CloseAsync<TVM>()그 ViewModel 타입에서 열려 있는(IsOpen) 것 중 맨 위 하나를 닫는다. 없으면 아무 일 없다.
IsOpen<TVM>()그 ViewModel 타입이 하나라도 열려 있으면 true, 한 번도 연 적 없으면 false(v0.4.0). ESC 같은 열기·닫기 토글, "이미 떠 있으면 다시 열지 않기"에 쓴다.
ScreenView.OpenAsync() · CloseAsync()화면 하나를 켜고 끄는 바탕 동작. 매니저가 부르고, 팝업은 닫기 요청을 받으면 스스로 CloseAsync를 부른다. 화면을 열 때는 매니저의 Open을 쓴다. 연출 중 새 요청이 오면 이전 것은 취소된다. 열려 있지 않으면(이미 닫혔거나 닫는 중) 닫기는 아무것도 안 한다.
ScreenView.IsOpen열기를 시작한 때부터 닫기를 시작할 때까지 true — 닫기 연출 중에도 false다(오브젝트는 연출이 끝날 때까지 켜져 있다). 누가 닫든(매니저·자기 버튼) 바뀐다. v0.4.0에서 IsClosing을 대신한다. 화면은 OpenAsync·CloseAsync(또는 매니저)로만 열고 닫는다 — SetActive를 직접 바꾸면 어긋난다.

닫힌 화면은 파괴되지 않고 꺼진 채 다시 쓰인다. 숨은 동안에도 ViewModel이 살아 이벤트를 받으므로 다시 열면 값이 바로 맞다. 같은 화면을 여러 개 띄우면 쉬는 인스턴스가 없을 때 새로 만든다. 닫기 연출 중에 다시 열면 새로 만들지 않고 그 인스턴스를 다시 연다(닫기 연출은 취소되고 창은 지금 크기에서 이어서 커진다).

팝업

  • AbstractPopupVM: CloseCmd(닫기 버튼·배경 → Dismiss), RequestClose(), Dismiss()(virtual — 기본은 RequestClose, 취소 콜백 등을 먼저 하려면 덮는다), ResetForOpen()(CloseCmd 되돌리기 — 덮으면 base를 부른다).
  • AbstractPopupView<T>: 필드 window(TransitionElement, 필수), closeButton·backgroundDim([Nullable]). 열고 닫는 동안 창·배경 연출을 함께 기다리고, 그동안 클릭을 막는다.
  • ViewModel이 RequestClose()를 부를 때만 닫힌다. 눌린 뒤 결과를 보고 닫을지 정한다(검증 실패면 안 닫기, 저장이 끝난 뒤 닫기). 누르기 전에 막을 것은 SetEnabled(false).

계속 떠 있는 화면(HUD)도 매니저로

HUD도 다른 화면처럼 프리팹을 매니저의 Screen View Prefabs에 등록하고, 시작을 맡은 컴포넌트가 Open<HudVM>(setup)으로 연다. 프리팹은 씬 오브젝트를 참조할 수 없으므로, 씬의 Model(플레이어 체력 등)은 시작 컴포넌트가 받아 setup으로 넘긴다.

public interface IHealth                          // 프로젝트 Model 예시
{
    float Current { get; }
    float Max { get; }
    event Action<float, float> Changed;           // (현재, 최대)
}

public class HudVM : AbstractViewModel
{
    public Bindable<float> Hp { get; } = new();
    public Bindable<float> MaxHp { get; } = new();
    public IReadOnlyBindable<float> HpRatio { get; }
    public IReadOnlyBindable<string> HpText { get; }

    private IHealth _health;

    public HudVM()
    {
        // 원본이 ViewModel 자신의 값이라 Own 하지 않는다
        HpRatio = Bindable.Combine(Hp, MaxHp, (hp, max) => max > 0f ? hp / max : 0f);
        HpText  = Bindable.Combine(Hp, MaxHp, (hp, max) => $"{hp:0} / {max:0}");
    }

    public void Setup(IHealth health)
    {
        _health = health;
        HandleChanged(health.Current, health.Max);   // 이벤트는 바뀐 것만 알리므로 지금 값을 먼저 읽는다
        health.Changed += HandleChanged;
    }

    // 열 때마다 지난 대상의 구독을 풀고 값을 비운다 — 다시 열어도 구독이 쌓이지 않게
    protected override void ResetForOpen()
    {
        Unsubscribe();
        ResetAll(Hp, MaxHp);
    }

    public override void Dispose()
    {
        Unsubscribe();
        base.Dispose();
    }

    private void Unsubscribe()
    {
        if (_health == null)
            return;
        _health.Changed -= HandleChanged;
        _health = null;
    }

    private void HandleChanged(float current, float max)
    {
        MaxHp.Value = max;
        Hp.Value = current;
    }
}

public class HudView : ScreenView<HudVM>
{
    [SerializeField] private GaugeElement hpGauge;
    [SerializeField] private TextViewElement hpText;

    protected override void Bind(HudVM vm)
    {
        hpGauge.Bind(vm.HpRatio);
        hpText.Bind(vm.HpText);
    }
}

07 / IMPORTANT NOTES

필수 주의사항

  • 생성자에서 구독하지 않는다: SO 같은 직렬화 필드는 역직렬화가 생성자 뒤에 채우고, 에디터도 직렬화하며 생성자를 부른다. 구독·Own·SO 파생 값은 IInitializable.Initialize()에 둔다. ViewModel에 [Serializable]이 없으면 SO 칸이 안 생기고 오류도 안 난다.
  • 바인딩 객체는 한 번만 만든다: View는 Awake에서 묶은 객체를 계속 든다. get-only 속성으로 두고, 열 때마다 바뀌는 것은 값과 Command.Action으로 바꾼다. 초기값은 생성자로(new(5)).
  • ResetForOpen은 손으로 쓴다: 빠뜨린 필드는 지난 값·콜백이 남고 컴파일러가 못 잡는다. setup이 넣는 것은 전부 되돌리고, Model 값·저장되는 양방향 값은 두지 않는다.
  • 팝업은 ViewModel이 닫기를 요청해야 닫힌다: 확인·취소 경로마다 RequestClose()(또는 Dismiss)를 부른다. 하위 팝업이 Initialize·Bind·ResetForOpen을 덮으면 base를 부른다 — 안 부르면 닫기 연결·CanvasGroup·CloseCmd 되돌리기가 빠진다.
  • 양방향 Element에는 원본 Bindable<T>만: 파생 값을 넘기면 에디터에서 Assert가 뜨고 조작이 ViewModel에 가지 않는다. 같은 Element를 두 번 Bind하면 두 번째가 첫 번째를 끊으므로, 원본이 둘인 Dropdown·OptionStepper는 Bind(options, selected) 한 번으로 묶는다.
  • 매니저 배치: 루트 Canvas 오브젝트, 씬 최상위, Screen Space - Overlay(Camera 모드면 씬마다 카메라가 바뀐다). 매니저가 있는 씬을 다시 불러도 둘이 되지 않게 한다 — 패키지는 중복을 막지 않는다. 화면 프리팹 루트는 켠 채로 저장하고, 모든 화면은 루트 Canvas 바로 아래에 둔다.
  • 닫힌 화면은 남는다: 꺼진 채 ViewModel이 계속 이벤트를 받고, 연 화면은 앱이 끝날 때까지 메모리에 남는다. 스크롤·토글처럼 View에 남은 상태는 그 화면의 PlayOpen에서 되돌린다.
  • 모든 화면은 매니저로 연다: HUD처럼 계속 떠 있는 화면도 프리팹으로 매니저에 등록하고 시작 담당 컴포넌트가 Open한다. 씬에 직접 두면 Awake 끝에서 꺼지고, 꺼 둔 채 저장하면 켜는 순간 다시 꺼진다. 대상이 바뀌면 닫고 다시 연다 — 켜진 채로 또 Open하면 두 번째 화면이 생긴다.
  • 상태와 사건을 구분한다: Bindable은 같은 값을 무시하고 구독 때 현재 값을 다시 부른다. 토스트처럼 매번 보여야 하는 것은 Signal — 구독 전 Fire는 사라지고, 꺼진 Element는 받은 알림을 버린다.

구조를 확장하거나 Element를 직접 만들 때 참고한다.

설계 결정 · ADR

ADR-01 · 바인딩은 제네릭으로 타입을 고정한다

상황
예전 MVP는 리플렉션과 형변환으로 반복 작업을 줄였지만, 성능에 문제가 있었고 값을 쓸 때마다 형변환을 해야 했다.
대안
리플렉션·형변환으로 연결(예전 MVP) / 제네릭 Bindable<T>와 값 타입이 정해진 Element를 코드로 연결.
선택
UI Toolkit의 Binding처럼 element.Bind(vm.값) 한 줄로 잇는다. Element는 UI에서 자주 쓰는 기능 단위로 잘게 나눈다(글 → TMP, 버튼 → Command 실행 등).
이유
실행 중 리플렉션과 형변환이 없어 성능 문제와 매번의 형변환이 사라지고, 값 타입이 맞지 않으면 컴파일 오류로 드러난다. 잘게 나눈 Element를 조합해 반복 작업을 줄인다.
감수한 단점
제네릭 MonoBehaviour는 컴포넌트로 붙일 수 없어 값 타입마다 구체 Element 클래스가 필요하다(NumberTextElement는 float에 int 오버로드). 목록(ItemListElement.Bind<TItem>)과 양방향 Element에 파생 값을 넘기는 실수는 실행 중에야 확인된다.

ADR-02 · ViewModel은 순수 C# 객체로 한다

상황
화면 상태와 입력 처리를 위젯·Unity 생명주기와 떼어 시험하고 재사용해야 한다.
대안
ViewModel도 MonoBehaviour / Presenter가 값을 바꾸고 위젯 갱신을 손으로 부름 / 순수 C# ViewModel + Bindable.
선택
AbstractViewModel : IDisposable. View가 소유하고 파괴될 때 Dispose한다.
이유
new로 만들어 EditMode 테스트가 바로 되고, 프리팹 컴포넌트는 View 하나다. 값이 바뀌면 묶인 Element가 따라가 "A·B 갱신" 호출을 빠뜨릴 일이 없다.
감수한 단점
OnDestroy·코루틴이 없다. 해제는 View가 대신 부르고, 시간 기반 연출은 Element·View의 DOTween이 맡는다.

ADR-03 · 구독은 Bind 하나, 구독 즉시 현재 값

상황
처음 값을 놓치거나 구독 해제를 잊는 실수가 흔하다.
대안
변경 event를 밖에 공개 / 구독 메서드 하나만 공개.
선택
IReadOnlyBindable<T>.Bind만 연다. 구독 즉시 현재 값으로 부르고 해제 핸들(IDisposable)을 돌려준다. 이름은 Element의 Bind와 같다 — 코드를 쓰며 정했고, 겹쳐도 이름 문제는 없다고 보고 그대로 두었다.
이유
화면을 처음 열 때 "전부 갱신"이 필요 없다. Element·파생 값·Own이 같은 핸들로 해제를 모은다.
감수한 단점
v0.4.0에도 구독 즉시 호출을 끄는 옵션이 없다 — 첫 값에 반응하면 안 되는 쪽이 직접 구분한다(PunchElement처럼). 상태가 아닌 사건은 Signal로 따로 둔다(ADR-09).

ADR-04 · Element는 필드로 잡고, 연결은 손으로 쓴다

상황
자식 찾기·드래그·AddListener 반복을 줄이되, 무엇이 무엇에 묶였는지는 코드에 드러나야 한다.
대안
자식 순서·문자열 이름으로 찾기 / 생성기가 만든 partial 속성 + 이름이 같으면 자동 연결 / [SerializeField] 필드 + 이름으로 채우기 + 손 연결.
선택
마지막. 에디터 버튼이 빈 필드를 같은 이름의 자식으로 채우고, Bind는 View에 직접 쓴다.
이유
계층 순서·문자열은 바뀌면 조용히 깨진다. 생성기는 프리팹이 있어야 속성이 생겨 코드를 먼저 쓸 수 없었다. 자동 연결은 손 연결과 겹치면 두 Element가 같은 값을 보게 되고, 연결이 코드에 다 드러나지 않는다.
감수한 단점
Element마다 필드 한 줄, 이름이 안 맞으면 끌어다 놓기. 빠진 참조는 실행 중 NullReferenceException으로 안다(빠진 참조 검사는 넣지 않았다).

ADR-05 · ViewModel은 View의 직렬화 필드로 둔다

상황
ViewModel이 설정 SO·이벤트 채널 같은 에셋을 써야 한다.
대안
View가 에셋을 들고 ViewModel 생성 메서드에서 생성자로 넘김 / ViewModel이 직접 [SerializeField]로 듦.
선택
ScreenView<T>의 [SerializeField] internal T viewModel = new T(). ViewModel이 자기 에셋을 직렬화한다.
이유
View에 ViewModel 생성 코드가 필요 없고, ViewModel이 쓰는 에셋이 인스펙터의 View 아래에 보인다. 복제(Instantiate)마다 ViewModel도 따로 생긴다.
감수한 단점
[Serializable]이 없으면 조용히 칸이 안 생긴다. 생성자에서 구독할 수 없어 IInitializable이 따로 있고, 생성자 매개변수를 쓸 수 없다(new() 제약).

ADR-06 · 화면 키는 ViewModel 타입, ViewModel을 돌려주지 않는다

상황
여는 쪽은 View를 몰라야 하고, 열 때마다 넣을 값이 있다.
대안
화면별 enum 키(레지스트리 항목) / 문자열 키 / ViewModel 타입 + setup 콜백.
선택
Open<TVM>(setup). 값은 setup에서 넣고, 반환값은 없다. HUD처럼 계속 떠 있는 화면을 포함해 모든 화면을 매니저로 연다.
이유
패키지만으로 끝나고 이름 바꾸기·사용처 찾기가 IDE로 된다. ViewModel을 들고 있다가 재사용된 다른 용도의 ViewModel에 값을 넣는 버그를 막는다. enum으로 여는 것이 필요하면 프로젝트에서 enum → Open<TVM>() 매핑만 얹는다.
감수한 단점
ViewModel 타입 하나에 프리팹 하나. 같은 화면이 여러 개 떠 있을 때 특정 하나를 밖에서 닫을 수 없다(맨 위만).

ADR-07 · 닫힌 화면은 꺼 두고 다시 쓰며, 열 때마다 ViewModel을 되돌린다

상황
매번 생성·파괴는 비용이 있고, 재사용하면 지난 setup의 값·콜백이 다음 열기에 남는다.
대안
열 때 생성·닫을 때 파괴 / View가 묶은 원본을 닫을 때 비움 / ViewModel 선언에 "열 때마다" 표시 / ViewModel의 ResetForOpen.
선택
매니저가 꺼진 인스턴스를 재사용하고, setup 직전에 항상 ResetForOpen을 부른다. 바인딩의 Reset() 기준은 "만든 직후"다.
이유
Instantiate·Awake가 다시 돌지 않고, 숨은 화면도 이벤트를 받아 값이 최신이다. 무엇을 되돌릴지는 ViewModel만 안다 — Element는 원본이 Model 값인지 setup 값인지 모른다.
감수한 단점
되돌릴 게 없는 ViewModel도 빈 override를 쓴다. 되돌릴 목록을 손으로 써서 빠뜨려도 컴파일러가 못 잡는다. 연 화면은 앱이 끝날 때까지 메모리에 남는다.

ADR-08 · 팝업 닫기는 ViewModel이 요청하고 View가 닫는다

상황
버튼을 누른 뒤 결과(검증·저장)에 따라 닫을지 정해야 하는데, ViewModel은 View를 모른다.
대안
한 버튼에 Command 여럿 묶기 / View가 Command를 감싸 실행 뒤 닫기 / ViewModel이 매니저를 듦 / 여는 쪽 콜백에서 닫기 / 버튼에 "부모 팝업 닫기" 컴포넌트.
선택
AbstractPopupVM.RequestClose() → CloseRequested Signal → AbstractPopupView가 CloseAsync.
이유
닫을지·언제 닫을지를 ViewModel이 정하고, 참조 방향(View → ViewModel)을 지킨다. 닫기 경로가 코드에 드러나 프리팹에 숨은 연결이 없다.
감수한 단점
모든 팝업 ViewModel이 AbstractPopupVM을 상속해야 한다. RequestClose를 빠뜨리면 안 닫힌다(눌러 보면 바로 보인다).

ADR-09 · 상태는 Bindable, 사건은 Signal

상황
토스트·데미지 숫자는 같은 값이 연달아 와도 매번 보여야 하고, 다시 묶을 때 지난 사건이 또 뜨면 안 된다.
대안
Bindable 재사용 / ViewModel의 C# event / 값을 저장하지 않는 Signal.
선택
Signal<T>. 받는 쪽 바탕 SignalElement<T>는 꺼져 있을 때 온 알림을 버린다.
이유
Element는 Bindable·Command·Signal만 알고, Bind가 IDisposable을 돌려줘 Element의 연결 바구니에 그대로 들어간다. 닫혀 숨은 화면에 토스트가 쌓이지 않는다.
감수한 단점
구독 전에 Fire된 것은 사라진다(의도). 인자 없는 Signal이 없어 팝업 닫기 요청도 Signal<bool>을 쓴다.

using MVVM.UGUI.Elements.Core;
using UnityEngine;
using UnityEngine.UI;

public class OnOffColorElement : VisualElement<bool>     // 켜지면 onColor, 꺼지면 offColor
{
    [SerializeField] private Graphic graphic;
    [SerializeField] private Color onColor = Color.green;
    [SerializeField] private Color offColor = Color.gray;

    protected override void HandleValueChanged(bool on) => graphic.color = on ? onColor : offColor;

    private void Reset() => graphic = GetComponent<Graphic>();
}
  • Awake를 믿지 않는다. 꺼진 채 만들어진 Element는 Awake보다 Bind(View의 Awake)가 먼저 온다. 원래 글·색·위치는 처음 값을 받을 때 읽고, 리스너 연결만 Awake에 둔다.
  • 바탕의 Bind가 먼저 Unbind하고 구독 핸들을 Bindings에 담는다. 직접 Bind 오버로드를 만들면 같은 규칙을 지킨다.
  • 트윈 규칙은 TweenValueElement에 있다: 첫 값·꺼져 있음·플레이 중이 아님·duration 0이면 바로 맞추고, 트윈 중 새 값은 이전 트윈을 Kill해 지금 위치에서 새 목표로, 트윈 중 꺼지면 목표로 바로 맞춘다.
  • DOTween은 본체 API만(DOTween.To·DOScale·DOPunchScale). Modules의 DOFade·DOFillAmount는 프로젝트마다 어셈블리 위치가 달라 패키지가 참조할 수 없다. 시작할 때 SetLink(gameObject), 기본 SetUpdate(true).
  • 피할 이름: TextElement·BindableElement(UnityEngine.UIElements에 있다). 폴더 이름은 복수형(Commands·Inputs·Texts) — 단수면 Command가 클래스가 아니라 namespace로 잡혀 컴파일이 깨진다. namespace는 폴더 경로를 따른다(NamespaceTests가 검사).
화면 관리 상세

자료구조와 맨 위 찾기

매니저는 ViewModel 타입 → (프리팹, 인스턴스 목록)을 든다. 프리팹은 처음 열 때 목록에서 prefab is ScreenView<TVM>인 것을 찾는다. 인스턴스 목록은 보관만 하고, 열린 순서는 계층의 형제 순서가 든다 — 열 때 SetAsLastSibling, 닫기는 그 타입에서 열려 있는(IsOpen) 것 중 GetSiblingIndex()가 가장 큰 것. IsOpen<TVM>()도 같은 목록을 본다. 그래서 모든 화면이 같은 부모(루트 Canvas) 바로 아래여야 한다.

열기 · 닫기 연출

  1. OpenAsync: IsOpen = true → 진행 중 전환을 취소 → 켜기 → PlayOpen(token) 대기.
  2. CloseAsync: 열려 있지 않으면 끝 → IsOpen = false → 진행 중 전환 취소 → PlayClose(token) 대기 → 끄기. 중간에 취소되면(새 열기) 끄지 않는다 — 그 열기가 이미 IsOpen을 켰다.
  3. 토큰은 destroyCancellationToken과 연결되어 파괴될 때도 취소된다. 하위 View는 받은 토큰을 트윈 대기에 넘겨야 취소가 먹힌다.
  4. 매니저로 다시 열 때 닫는 중인 인스턴스는 열려 있지 않으므로 그 인스턴스를 다시 연다. v0.3.0까지는 켜져 있다는 이유로(activeSelf + IsClosing) 고르지 않아 두 번째 인스턴스가 생겼다.

Canvas 구성

씬에 루트 Canvas 하나(CanvasScaler·렌더 모드), 각 화면 프리팹 루트에 중첩 Canvas(Override Sorting 끔) — 한 화면의 변경이 다른 화면의 다시 그리기를 부르지 않게 한다. 클릭을 받는 화면은 루트에 GraphicRaycaster도 둔다(Graphic은 가장 가까운 Canvas에 등록돼 루트의 Raycaster가 못 본다). 숨기기는 SetActive다 — 숨은 동안 스크립트가 멈춘다. 열림 판단은 IsOpen으로 한다(v0.3.0까지는 activeSelf).

MVVM.UGUI는 자동 참조라 Assembly-CSharp 코드는 바로 쓸 수 있다. 자체 asmdef를 쓰는 코드는 MVVM.UGUI를 참조하고, OpenAsync의 UniTask를 다루면 UniTask도 참조한다. 패키지 EditMode 테스트는 v0.4.0에서 140개 통과(Unity 6000.3, 2026-10-22).

프리팹 미등록OpenAsync가 오류 로그만 남기고 끝난다.매니저의 Screen View Prefabs에 등록한다.

화면을 씬에 직접 둠Awake 끝에서 꺼진다. 꺼 둔 채 저장했다면 켜는 순간 Awake가 돌고 다시 꺼진다. ResetForOpen도 불리지 않는다.프리팹으로 매니저에 등록하고 시작 담당 컴포넌트가 Open으로 연다.
열린 화면을 또 Open쉬는 인스턴스가 없어 새로 만든다 — HUD가 둘이 된다.대상을 바꿀 때는 CloseAsync 뒤 OpenAsync. 하나만 띄울 화면은 IsOpen<TVM>()로 먼저 확인한다.
SetActive로 화면을 직접 켜고 끔IsOpen과 실제 상태가 어긋나 맨 위 찾기·다시 쓰기·IsOpen<TVM>()가 틀린다.열고 닫기는 매니저 또는 OpenAsync·CloseAsync로만.
setup 대상 구독을 안 풂다시 열 때마다 구독이 쌓이고, 지난 대상의 알림도 계속 받는다.Setup에서 구독, ResetForOpen·Dispose에서 해제.
화면을 루트 Canvas 밖으로 옮김맨 위 판단(형제 순서)이 어긋난다.매니저가 만든 자리(루트 Canvas 직속)를 유지한다.
매니저 중복막지 않는다. 둘 다 DontDestroyOnLoad로 남는다.매니저가 있는 씬을 다시 불러도 하나만 남게 프로젝트에서 관리한다.
Element 필드 비어 있음Bind에서 NullReferenceException.이름으로 채우기 경고를 확인한다. [Nullable] 필드는 ?.로 부른다.
양방향 Element에 파생 값에디터 Assert, 조작이 ViewModel에 쓰이지 않는다.원본 Bindable<T>를 넘긴다.
항목 프리팹 타입 틀림오류 로그, 목록을 그리지 않는다.ItemView<TItem>의 TItem을 목록과 맞춘다.
생성자에서 SO 구독필드가 아직 비었거나, 에디터 직렬화 때도 생성자가 돈다.IInitializable.Initialize()로 옮긴다.
오래 사는 원본의 파생 값을 Own하지 않음컴파일은 된다. View가 파괴돼도 원본이 파생 값을 붙잡아 계속 다시 계산한다.SO·전역 원본이면 Own. 리뷰로 확인한다.

팝업 base 호출 누락닫기 연결·CanvasGroup·CloseCmd 되돌리기가 빠진다.Initialize·Bind·ResetForOpen을 덮으면 base를 부른다.
하위 View가 토큰을 안 넘김연출 중 취소·파괴가 트윈 대기를 끊지 못한다.PlayOpen·PlayClose의 토큰을 트윈 대기에 넘긴다.
EditMode에서의 트윈플레이 중이 아니면 늘 바로 맞추는 경로다.트윈 연출은 플레이 모드에서 확인한다.
변경 후 확인 체크리스트

구성

  • 프리팹이 매니저 목록에 있고 루트가 켜져 있는가.
  • 이름으로 채우기에서 경고 없이 필드가 채워지는가.
  • ViewModel에 [Serializable]이 있고 SO 칸이 보이는가.
  • SO 구독·파생 값이 Initialize에 있고, 오래 사는 원본은 Own 했는가.
  • 팝업 하위 클래스가 base를 부르는가.

실행

  • 처음 열 때 값이 바로 보이는가.
  • 다른 setup으로 다시 열면 지난 값·콜백이 남지 않고, 구독이 쌓이지 않는가.
  • 확인·취소·닫기 버튼·배경이 모두 닫히는가.
  • 열기·닫기 연출 중 클릭이 막히는가.
  • 같은 화면을 둘 띄우면 위부터 닫히는가. 닫는 중에 다시 열어도 화면이 하나인가. 씬 전환 뒤에도 다시 열리는가.
