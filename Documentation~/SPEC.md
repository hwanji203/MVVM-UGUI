# MVVMSystem 명세 — 코드 없는 공부용

> `DESIGN.md` 와 같은 내용을 **코드 없이** 적은 것. 무엇을 해야 하는지 · 왜 그런지 · 어디서 틀리기 쉬운지 · 어떻게 확인하는지만 있다.
> 메서드 모양 (이름 · 매개변수 · 반환 타입) 과 구현 방법은 직접 정한다. 정한 것은 `ROADMAP.md` "정한 세부" 에 적는다.
> `DESIGN.md` 에는 코드 예시가 있다 — 직접 짠 뒤 비교할 때만 연다.
>
> 각 절의 구성: **역할** → **지켜야 할 동작** (체크리스트) → **왜** → **함정** → **확인** (테스트로 옮길 상황).
> 정해진 이름 (`Bindable`, `Element` …) 은 다른 부품 · 생성기와 맞물리므로 그대로 쓴다.

## 0. 전체 그림

### 목표

화면 하나를 만들 때 반복되는 연결 코드를 거의 없앤다. 화면마다 직접 쓰는 것은 **ViewModel 하나, View 하나, 프리팹** 뿐이어야 한다. 그리고 이 틀은 **어떤 프로젝트에든** 붙어야 하므로 특정 이벤트 · 사운드 시스템을 몰라야 한다.

### 네 층

| 층 | 하는 일 | 무엇으로 |
| --- | --- | --- |
| Model | 게임 쪽 데이터 · 규칙 · 이벤트. 틀은 모른다 | 프로젝트 코드 |
| ViewModel | 화면 하나가 보여줄 상태와, 버튼이 할 일 | 일반 C# 클래스 (MonoBehaviour 아님) |
| View | 프리팹 루트에 붙어 ViewModel 을 만들고 위젯과 잇는다 | MonoBehaviour |
| Element | 다시 쓰는 위젯 하나 (글자 · 게이지 · 버튼 …) | MonoBehaviour |

### 누가 누구를 아는가

- View 는 ViewModel 을 안다. ViewModel 은 Model 쪽 (이벤트 · 설정 데이터) 을 안다. **반대 방향으로는 모른다.**
- 아래에서 위로 알릴 때는 이벤트를 쓴다. 보내는 쪽은 누가 받는지 모른다.
- Element 는 "값 상자" 와 "명령" 만 안다. 어느 화면의 어느 ViewModel 인지 모른다.

**생각해 볼 것**: 설정창에서 볼륨을 바꾸면 Model 이 ViewModel 을 알아야 할 것 같지만 아니다. 왜 아닌가? (값을 바꾸는 쪽이 누구인지, 그 방향이 어느 쪽인지 따져 본다.)

### 처음 값

이벤트는 **바뀐 것** 만 알려준다. 화면이 만들어지는 순간의 값은 따로 받아야 한다. 기본은 "시작할 때 오는 이벤트에 처음 값을 담는다", 중간에 여는 화면만 "읽기 전용 상태나 설정 데이터를 생성할 때 받아 읽는다".

## 1. 단계 UI0 — 바인딩

이 단계는 Unity 없이 테스트할 수 있다. 화면도 위젯도 없이, 값과 알림만으로 끝까지 확인한다.

### 1.1 `Bindable<T>` — 값 상자

**역할**: 값 하나를 들고 있다가, 값이 바뀌면 구독자들에게 알린다.

**지켜야 할 동작**
- [ ] 값을 읽을 수 있고, 쓸 수 있다.
- [ ] 쓸 때 **이전과 같은 값이면 아무에게도 알리지 않는다.**
- [ ] 다른 값이면 구독자 **전부** 에게 새 값을 알린다.
- [ ] 구독할 때 기본으로 **현재 값을 그 자리에서 한 번** 받는다. 원하면 이걸 끌 수 있다.
- [ ] 구독하면 "구독을 끊는 손잡이" 를 돌려받는다. 그걸로 끊으면 그 뒤로는 알림이 안 온다.
- [ ] 구독하는 길은 **이 구독 메서드 하나뿐** 이다. 이벤트를 밖에 그대로 열어 두지 않는다.
- [ ] 처음 값을 정해서 만들 수 있다.

**왜**
- 같은 값 무시: 쓸데없는 화면 갱신을 막고, 양방향 연결 (3.2) 에서 값이 계속 왕복하는 것을 끊는 보험이 된다.
- 구독 즉시 현재 값: 화면을 처음 열 때 "전부 한 번 갱신" 코드가 필요 없어진다.
- 구독 길이 하나: 이벤트를 그대로 열면 "처음 값을 못 받음" · "해제를 잊음" 이 쉽게 생긴다.

**함정**
- "같은 값" 을 무엇으로 비교할지. `==` 는 제네릭 타입에 바로 못 쓴다. .NET 에는 타입마다 알맞은 비교를 골라 주는 기본 비교 도구가 있다.
- 리스트나 클래스처럼 **안쪽만 바뀌는** 값은 이 상자가 알 수 없다 (같은 객체라서). 목록은 1.4 의 별도 상자를 쓰고, 그 밖에는 새 값을 통째로 넣는다는 규칙을 둔다.
- 알림 도중에 누군가 구독을 끊거나 새로 구독하면? 어떻게 동작해야 안전할지 정한다.
- 끊는 손잡이를 **두 번** 쓰면? 에러 없이 아무 일도 없어야 한다.

**확인**
- 같은 값을 넣으면 구독자가 안 불린다.
- 다른 값을 넣으면 구독자 둘이 모두 새 값을 받는다.
- 구독하는 순간 현재 값을 한 번 받는다 / 끄고 구독하면 안 받는다.
- 끊은 뒤 값을 바꾸면 안 불린다.

### 1.2 읽기 전용 상자

**역할**: 값을 **읽고 구독만** 할 수 있는 모습. 쓰기는 막힌다.

**지켜야 할 동작**
- [ ] 1.1 의 상자는 이 모습으로도 넘길 수 있다.
- [ ] 이 모습으로는 값을 쓸 수 없다 (컴파일러가 막는다).

**왜**: 원본에서 계산된 값 (1.3) 은 누가 직접 쓰면 안 된다. 그리고 위젯이 "나는 읽기만 한다" 를 타입으로 드러낼 수 있다.

**노출 규칙 (정해진 것)**

| ViewModel 이 밖에 보여주는 것 | 어떤 모습으로 |
| --- | --- |
| 계산된 값 | 읽기 전용 |
| 원본 상태 | 쓰기 가능한 상자를 읽기 전용 필드로 (값 하나에 두 줄을 쓰지 않으려고) |
| 슬라이더 · 토글처럼 위젯이 쓰는 값 | 쓰기 가능 |

### 1.3 파생 값 — 다른 상자로부터 계산되는 상자

**역할**: "HP 비율 = HP ÷ 최대 HP" 처럼 다른 상자들로 계산되는 값을 상자로 만든다.

**지켜야 할 동작**
- [ ] 원본 하나로 계산하는 것과, 원본 두 개 (필요하면 세 개) 로 계산하는 것.
- [ ] 원본 중 **어느 하나라도** 바뀌면 다시 계산해서 자기 값을 바꾼다.
- [ ] 결과는 읽기 전용 상자로 돌려준다.
- [ ] 만드는 순간 이미 올바른 값을 들고 있다.
- [ ] 다시 계산한 결과가 이전과 같으면 자기 구독자에게 알리지 않는다 (1.1 규칙 그대로).

**왜**: 예전 방식은 "HP 가 바뀌면 게이지 갱신, 글자 갱신" 을 이벤트마다 적었다. 파생 값은 그 관계를 **만들 때 한 번** 적는다. HP 를 바꾸는 이벤트가 피격 · 회복 · 최대치 증가로 늘어도 갱신 코드는 늘지 않는다.

**함정**
- 원본을 구독할 때 "구독 즉시 현재 값" 을 그대로 쓰면 만들 때 계산이 여러 번 일어난다. 문제는 없지만 의도를 정한다.
- 원본 두 개를 쓸 때, 하나가 바뀌면 **다른 하나의 현재 값** 이 필요하다. 어디서 얻는가?
- 파생 값의 구독은 따로 끊지 않는다 (같은 ViewModel 안에서 같이 버려지니까). 정말 괜찮은지 1.6 의 수명 규칙과 맞춰 본다.

**확인**
- HP 를 바꾸면 비율 상자의 구독자가 새 비율을 받는다.
- 최대 HP 만 바꿔도 다시 계산된다.
- 결과가 같게 나오는 변화 (예: 둘 다 두 배) 에서는 알림이 없다.

### 1.4 `Command` — 버튼이 할 일

**역할**: 인자 없는 동작 하나와, "지금 실행할 수 있나" 를 함께 들고 있다.

**지켜야 할 동작**
- [ ] 실행하면 맡긴 동작이 불린다.
- [ ] "실행할 수 있나" 는 **읽기 전용 상자 (bool)** 다. 안 주면 늘 가능.
- [ ] 실행할 수 없는 상태에서 실행하면 **아무 일도 없다.**

**왜**: 버튼이 잠겨 있는지와 눌렀을 때 할 일을 한곳에. "실행할 수 있나" 가 상자라서 버튼이 구독해 잠김 표시를 알아서 바꾼다.

**확인**: 가능 → 실행 → 불림 / 불가능으로 바꿈 → 실행 → 안 불림.

### 1.5 `BindableList<T>` — 개수가 바뀌는 목록

**역할**: 손패 · 상점 칸처럼 한 화면 안에서 항목이 늘고 주는 목록. 무엇이 어떻게 바뀌었는지 알린다.

**지켜야 할 동작** (알림 종류는 직접 정해도 된다 — 시작점)
- [ ] 추가 (어느 위치에 무엇이)
- [ ] 삭제 (어느 위치에서)
- [ ] 교체 (어느 위치가 무엇으로)
- [ ] 전체 다시 (비우기 등)

**왜**: 1.1 의 상자는 목록 안쪽 변화를 모른다. 그리고 "통째로 다시 그리기" 보다 "이 칸만 추가" 가 화면에 싸다.

**함정**: 같은 **화면** 을 여러 개 띄우는 것 (4.3) 과 헷갈리지 않는다. 이건 한 화면 안의 항목 목록이다.

**확인**: 각 동작마다 알림 종류 · 인덱스가 맞는지, 여러 동작을 이어서 했을 때 순서가 맞는지.

### 1.6 `ViewModel` 기반 — 구독 맡기기

**역할**: 모든 화면 ViewModel 의 부모. **"오래 사는 것" 의 구독 손잡이를 맡아 두었다가, 정리할 때 한꺼번에 끊는다.** 그게 전부다.

**지켜야 할 동작**
- [ ] 끊는 손잡이를 맡길 수 있다 (자식 클래스만).
- [ ] 정리하면 맡긴 것을 전부 끊는다.
- [ ] 정리는 자식이 덧붙일 수 있다 (자식은 자기 정리를 하고 부모 정리를 부른다).
- [ ] **특정 이벤트 시스템 (DevLib 채널 등) 용 도우미는 넣지 않는다** (정해진 것). 그런 구독은 각 프로젝트의 ViewModel 이 직접 하고 직접 푼다.

**언제 끊어야 하나** — ViewModel 보다 **오래 사는 것** 을 구독했을 때만:

| 구독한 것 | 끊어야 하나 | 왜 |
| --- | --- | --- |
| 자기 자신의 상자 · 파생 값 | 아니요 | ViewModel 과 같이 버려진다 |
| 프로젝트의 이벤트 채널 (에셋) | 예 | 게임 내내 살아서 죽은 ViewModel 을 붙잡는다 |
| 설정 데이터 (에셋) 의 변경 알림 | 예 | 같은 이유 → 여기 맡긴다 |

**왜 끊어야 하나**: 안 끊으면 오래 사는 쪽이 죽은 ViewModel 을 계속 붙잡는다. 메모리에 남고, 이미 닫힌 화면의 코드가 계속 돈다.

**확인**: 손잡이 둘을 맡기고 정리 → 둘 다 끊겼다 / 정리를 두 번 해도 에러 없음.

### 1.7 수명 규칙 (다음 단계들이 지켜야 하는 것)

- ViewModel 은 MonoBehaviour 가 아니라서 스스로 파괴 시점을 모른다 → **View 가 파괴될 때 View 가 ViewModel 을 정리한다.**
- 위젯은 자기 연결을 들고 있다가 **자기가 파괴될 때 스스로 끊는다.** 그래서 View 가 연결 목록을 따로 들 필요가 없다.
- **닫힌 (꺼진) 화면은 정리하지 않는다.** 닫혀 있는 동안에도 이벤트를 받아 값이 최신으로 유지되고, 다시 열면 바로 맞다.

## 2. 단계 UI2 — 기본 Element

### 2.1 값 위젯의 공통 뼈대

**역할**: "상자 하나에 묶여서, 값이 오면 화면에 반영한다" 를 모든 위젯이 공유한다. 각 위젯은 **"값이 오면 어떻게 보일지" 한 가지만** 구현한다.

**지켜야 할 동작**
- [ ] 묶기: 읽기 전용 상자를 받아 구독한다. 구독하는 순간 현재 값이 반영된다.
- [ ] 다시 묶으면 **이전 연결을 먼저 끊는다.**
- [ ] 연결만 끊는 방법도 있다.
- [ ] 위젯이 파괴되면 스스로 끊는다.
- [ ] 묶기는 돌려주는 것이 없다 (정해진 것 — 끊는 책임이 위젯에 있으므로 밖에서 손잡이를 들 이유가 없다).
- [ ] 필요한 Unity 컴포넌트 (글자 · 이미지 · 슬라이더) 는 인스펙터 필드로 받고, **컴포넌트를 처음 붙일 때 같은 오브젝트에서 알아서 채운다** (Unity 가 붙일 때 부르는 함수가 있다).

**함정**
- 이름: Unity 의 UI Toolkit 에 이미 `TextElement` · `BindableElement` 가 있다. 겹치지 않게.
- 부모 클래스의 파괴 처리를 자식이 덮어쓰면 연결이 안 끊긴다. 자식이 덮어쓸 수 있게 하되 부모 것도 불리게 만든다.

### 2.2 양방향 위젯 (슬라이더 · 토글)

**역할**: 화면 → ViewModel 방향도 있다. 사용자가 조작하면 상자의 값을 바꾼다.

**지켜야 할 동작**
- [ ] 쓰기 가능한 상자를 받는다 (읽기 전용으로는 묶을 수 없게 — "이 위젯은 값을 쓴다" 가 드러나게).
- [ ] 사용자가 조작하면 상자 값을 바꾼다. **이때 알림이 나가는 것이 맞다** — 같은 값을 쓰는 다른 곳 (숫자 라벨, 실제 볼륨 적용) 이 따라와야 하니까.
- [ ] 상자 값이 바뀌어 위젯에 반영할 때는 **위젯 자신의 "값 바뀜" 이벤트가 다시 나가지 않게** 한다.

**생각해 볼 것**: 조작 → 상자 → 알림 → 위젯에 반영 → (위젯 이벤트?) → 상자 → … 이 고리를 끊는 곳이 어디인가? 답은 두 겹이다. 하나는 Unity UGUI 위젯이 제공하는 기능, 하나는 1.1 의 규칙.

**함정**: 위젯이 값을 고쳐서 받는 경우 (최대값을 넘김, 정수로 반올림) 화면과 상자가 어긋난다. **범위 제한은 ViewModel 이 값을 넣을 때** 한다는 규칙으로 막는다.

### 2.3 위젯 목록

| 위젯 | 묶는 것 | 할 일 |
| --- | --- | --- |
| Element (공통 부모) | — | 값 없이 "찾아 꺼내기" 만 할 위젯도 이것 (특수 연출용) |
| LabelElement | 글자 | 프리팹에 적힌 원래 글에 자리 표시 (`{0}`) 가 있으면 그 자리에 넣고, 없으면 통째로 바꾼다. 원래 글은 처음에 기억해 둔다 |
| GaugeElement | 0~1 실수 | 채움 정도. 부드럽게 (트윈) |
| CooldownElement | 0~1 실수 | 쿨다운 표시 (모양은 직접 정함) |
| ButtonElement | 명령 | 누르면 실행. "실행할 수 있나" 가 거짓이면 잠김 표시. 클릭 소리 (2.5) |
| SliderElement | 실수 (양방향) | 2.2 |
| ToggleElement | bool (양방향) | 2.2 |
| SwitchElement | 정수 | 자식 중 그 번호 하나만 켠다 |
| VisibleElement | bool | 켜고 끄기 (+ 페이드는 선택) |

### 2.4 꺼진 오브젝트 · 트윈 중

- 꺼진 오브젝트에도 구독은 살아 있다 → 값은 반영돼야 한다.
- 그런데 꺼진 오브젝트에서는 애니메이션이 제대로 안 돈다 → **꺼져 있으면 트윈 없이 바로 최종 값으로.**
- 트윈 중에 새 값이 오면 이전 트윈을 멈추고 **지금 위치에서** 새 목표로.
- 트윈은 오브젝트가 파괴되면 같이 끝나게 묶는다 (DOTween 에 그런 옵션이 있다).

### 2.5 클릭 소리

**역할**: 버튼 소리를 화면 코드가 아니라 버튼이 낸다. 그런데 틀은 사운드 시스템을 모른다.

**정해진 구조**
- 틀에는 **"소리를 낸다" 는 동작 하나만 가진 추상 ScriptableObject** 가 있다.
- 틀은 그것의 **기본 구현** 하나를 준다 (오디오 클립 하나를 재생).
- 버튼은 그 SO 를 인스펙터로 들고, 눌리면 그 동작만 부른다.
- 프로젝트는 자기 사운드 시스템으로 구현한 SO 를 만들어 끼우면 된다 (프로젝트 연결점 1).

**직접 정할 것**: 버튼을 붙일 때 기본 소리 SO 를 어떻게 자동으로 채울지 · 잠긴 버튼을 누르면 다른 소리를 낼지 · 토글 · 슬라이더에도 소리를 줄지.

**생각해 볼 것**: ScriptableObject 의 기본 구현은 씬에 있는 것이 아니다. 소리를 내려면 무엇이 필요하고, 그걸 어디서 얻을까?

### 2.6 확인 (수동)

빈 씬에 위젯마다 하나씩 놓고, 테스트용 컴포넌트에서 상자 값을 바꿨을 때 화면이 따라가는지 본다. 슬라이더를 끌었을 때 같은 상자에 묶인 라벨이 따라오는지 본다. **어떻게 확인했는지를 기록한다.**

## 3. 단계 UI3 — View 와 생성기

### 3.1 View 의 할 일

**역할**: 프리팹 루트에 붙는다. ViewModel 을 만들고, 위젯과 잇고, 파괴될 때 ViewModel 을 정리한다.

**지켜야 할 동작**
- [ ] 모든 화면 View 의 부모는 **어떤 ViewModel 을 쓰는지를 타입으로** 안다 (제네릭).
- [ ] 순서: 시작할 때 **ViewModel 만들기 → 자동 연결 → 손 연결.** 파괴될 때 ViewModel 정리.
- [ ] ViewModel 을 만드는 방법은 각 화면이 정한다 (필요한 SO 를 인스펙터로 들고 있다가 넘긴다).
- [ ] 자동 연결은 생성된 코드가, 손 연결은 화면 개발자가 채운다. 둘 다 비어 있어도 된다.
- [ ] 같은 위젯을 손으로 다시 묶으면 손 연결이 이긴다 (2.1 의 "다시 묶으면 이전 끊기" 덕분).
- [ ] 각 화면 View 는 partial 클래스다 (생성된 파일과 손으로 쓴 파일이 합쳐진다).

### 3.2 생성기 — 위젯 꺼내기

**역할**: 프리팹 안의 위젯을 꺼내는 **타입 있는 속성** 을 코드로 만들어 준다. 그래서 화면 개발자는 위젯을 이름으로 바로 쓴다 (찾기 · GetComponent · 인스펙터 드래그 없음).

**지켜야 할 동작**
- [ ] 대상: View 아래에서 **Element 가 붙은 자식들.**
- [ ] 생성기는 그 위젯들의 **참조를 View 의 배열에 저장** 하고, 그 배열 칸을 꺼내는 속성을 생성 파일에 쓴다.
- [ ] 속성 이름 = 오브젝트 이름 (C# 에서 쓸 수 있게 다듬음). 속성 타입 = 실제 붙은 Element 의 타입.
- [ ] 생성 파일은 View 스크립트 옆에, 이름은 정해진 규칙으로. 사람이 손대지 않는 파일.
- [ ] 안쪽에 다른 View (화면 안의 화면 · 목록 항목) 가 있으면 그 아래는 그쪽 소관이라 건너뛴다.
- [ ] 생성한 뒤 누가 위젯을 바꿔서 배열과 속성이 어긋나면, 에디터와 실행 시작 때 알린다 (어느 속성 · 기대 타입 · 실제 타입).

**왜 배열 + 속성인가**: 위젯마다 필드를 생성하면, 필드가 생기려면 컴파일이 끝나야 하고, 그 뒤에야 참조를 넣을 수 있다 (두 단계 · 기다림). 배열은 이미 있으니 참조를 바로 넣고, 속성 코드만 쓰면 **한 번에 끝난다.**

**왜 계층 순서가 아니라 참조인가**: 예전 방식은 계층 순서 번호로 찾아서, 오브젝트 순서만 바꿔도 깨졌다.

**함정**
- 같은 이름의 위젯이 둘이면? (멈추고 알리는 것으로 시작 — 직접 정해도 됨)
- 오브젝트 이름에 공백 · 숫자 시작 · 특수문자가 있으면?
- 생성 결과가 이전과 같으면 **파일을 다시 쓰지 않는다.** 다시 쓰면 Unity 가 재컴파일하고, 컴파일 뒤 생성 → 또 재컴파일 … 이 될 수 있다.

### 3.3 생성기 — 자동 연결

**역할**: 위젯 이름과 같은 이름의 ViewModel 멤버가 있으면 **연결 코드도 생성** 한다.

**지켜야 할 동작**
- [ ] 비교할 ViewModel = 그 View 가 부모 제네릭에 넣은 타입.
- [ ] 짝 조건: **이름이 완전히 같고** (접미사 떼기 같은 규칙 없음 — 정해진 것), 그 멤버의 타입 (상자 · 읽기 전용 상자 · 명령 · 목록) 을 그 위젯이 묶을 수 있을 때.
- [ ] 짝이면 생성 파일의 자동 연결 부분에 연결 한 줄.
- [ ] 이름은 같은데 타입이 안 맞으면 **경고하고 만들지 않는다.**
- [ ] 짝이 없는 위젯 목록을 알려 준다 (손으로 묶어야 하거나, 이름이 바뀌어 빠진 것).
- [ ] 비교는 **에디터에서 생성할 때만** 한다. 실행 중에는 생성된 평범한 코드가 돈다 (실행 중 리플렉션 없음).
- [ ] **ViewModel 쪽 선언은 생성하지 않는다** (정해진 것 — 생성하면 쓰기 가능한 상자가 되어 파생 값을 못 쓰고, 프리팹이 ViewModel 의 모양을 정하게 된다).

**함정**: "이 위젯이 이 타입을 묶을 수 있나" 를 어떻게 판단할까? 위젯 클래스가 받을 수 있는 묶기 메서드들을 에디터에서 살펴봐야 한다. 상속 (쓰기 가능한 상자는 읽기 전용 상자이기도 하다) 도 고려한다.

### 3.4 언제 생성하나 (정해진 것)

- 프리팹을 **저장할 때** (Unity 에 프리팹 편집 화면 저장 시점을 알려주는 이벤트가 있다).
- **스크립트 컴파일이 끝났을 때** (ViewModel 멤버 이름이 바뀌었을 수 있으니 다시 비교).
- View 인스펙터의 **버튼** (손으로 다시 만들 때).

### 3.5 확인

- 테스트 프리팹: 위젯 셋 (이름이 맞는 것 둘, 다른 것 하나) + 타입이 안 맞는 것 하나 + 안쪽 View 하나.
- 생성 결과: 속성 넷 (안쪽 View 아래 제외), 자동 연결 둘, 경고 하나, 짝 없는 목록에 하나.
- 같은 내용으로 다시 생성하면 파일이 안 바뀐다.
- 오브젝트 순서를 바꿔도 동작한다.

## 4. 단계 UI4 — 화면 열기 · 닫기

### 4.1 `ScreenManager`

**역할**: 한 씬의 화면들을 만들고 열고 닫는다.

**지켜야 할 동작**
- [ ] 씬에 두는 **평범한 컴포넌트** 다. 싱글톤 아님 (프로젝트 규칙).
- [ ] 자기 씬의 화면 프리팹 목록을 인스펙터로 들고, 시작할 때 만들어 둔다.
- [ ] 바깥에 주는 것은 **"이 종류의 화면 열기"** 와 **"닫기"** 메서드뿐 (정해진 것). 이벤트로 여는 것은 프로젝트가 잇는다 (연결점 2).
- [ ] 팝업은 **스택** 이다 — 닫기는 맨 위부터.
- [ ] "이 화면이 열려 있으면 저 요청은 무시" 같은 판단은 여기서 한다. **화면끼리는 서로 모른다.**

**왜**: 예전 방식은 화면 클래스마다 `static bool` 을 두고 서로 확인했다. 화면이 늘수록 서로를 알아야 했고, static 이라 씬을 다시 불러도 값이 남았다.

### 4.2 `PopupView`

**역할**: 팝업 화면 공통 동작. 각 팝업은 "어느 위젯이 창 · 배경 · 닫기 버튼인지" 만 알려준다 (생성된 속성으로).

**지켜야 할 동작**
- [ ] 열기: 창이 커지며 나타나고, 배경이 어두워지고, 입력을 받는다.
- [ ] 닫기: 반대로. 애니메이션이 **끝난 뒤** 꺼지고 "닫힘 완료" 를 알린다.
- [ ] 닫히는 동안에는 입력을 막는다 (Unity 의 Canvas 그룹으로).
- [ ] 닫기 버튼들 (배경 포함 가능) 을 누르면 닫힌다.
- [ ] 게임이 일시정지 (시간 배율 0) 여도 애니메이션이 돈다.
- [ ] 이미 열려 있는데 또 열기 / 닫는 중에 다시 열기 — 어떻게 할지 정한다.

### 4.3 같은 화면 여러 개

**역할**: 확인 팝업처럼 같은 화면이 동시에 여러 개 뜰 수 있다.

**지켜야 할 동작**
- [ ] 열기 요청은 **ScreenManager 하나만** 받는다. 쉬는 인스턴스가 있으면 그걸, 없으면 새로 만든다.
- [ ] 처음엔 **열 때 만들고 닫을 때 파괴** 로 시작한다 (정해진 것). 자주 뜨는 것이 생기면 Unity 내장 오브젝트 풀로.
- [ ] 파괴되는 인스턴스는 1.7 대로 ViewModel 이 정리된다.

**왜**: 예전 방식은 인스턴스 N 개가 **모두** 같은 이벤트를 받아서, 하나만 열리게 하려고 상태 머신이 필요했다. 받는 쪽을 하나로 만들면 그게 사라진다.

### 4.4 확인

팝업 열기 · 닫기 · 배경 눌러 닫기 · 두 개 겹쳐 띄우고 위부터 닫기 · 일시정지 중 열기.

## 5. 단계 UI5 — 목록

### 5.1 `ListElement` 와 항목 View

**역할**: 1.5 의 목록에 묶여서, 항목마다 항목 프리팹을 만들고 항목 View 를 잇는다.

**지켜야 할 동작**
- [ ] 묶으면 현재 항목들을 전부 만든다.
- [ ] 추가 · 삭제 · 교체 · 전체 다시 알림을 받아 **바뀐 칸만** 처리한다.
- [ ] 항목 View 도 3.1 과 같은 방식 (자기 ViewModel · 생성된 속성 · 자동 연결) 이다.
- [ ] 항목 프리팹이 만들어지는 위치와 순서가 목록 순서와 맞다.

**함정**: 항목 View 를 다시 쓰면 (풀) 이전 항목의 연결이 남지 않아야 한다 — 2.1 의 "다시 묶으면 이전 끊기" 가 여기서 중요하다.

**확인**: 추가 · 중간 삭제 · 교체 · 비우기가 화면 순서대로 반영되는지.

## 6. 패키지 · 프로젝트 연결

### 6.1 패키지 규칙

- 위치: 이 저장소 = 패키지 루트. 런타임 코드 · 에디터 코드 · 테스트는 각각 자기 asmdef 폴더에.
- **Unity 6000.3 에서 되는 것만** 쓴다 (팀 프로젝트가 6000.3).
- **DevLib 같은 특정 프로젝트 코드를 참조하지 않는다.**
- 의존: UGUI (TextMeshPro 포함). DOTween 은 패키지 의존성으로 선언할 수 없어서, 쓰는 프로젝트에 설치되어 있어야 한다.
- 에디터 코드는 반드시 에디터 전용 asmdef 에 (안 그러면 빌드에 섞여 깨진다).

### 6.2 프로젝트와 잇는 곳 (둘 다 선택)

| 연결점 | 틀이 주는 것 | 프로젝트가 할 일 | 안 이으면 |
| --- | --- | --- | --- |
| 1. 클릭 소리 | 소리 SO 추상 + 기본 구현 | 자기 사운드 시스템으로 구현한 SO 하나 | 기본 구현 |
| 2. 화면 열기 · 닫기 | ScreenManager 의 열기 · 닫기 메서드 | 자기 이벤트를 받아 그 메서드를 부르는 컴포넌트 하나 | 직접 호출 |

Project_B 에서는 연결점 1 = DevLib 사운드 이벤트를 쏘는 SO, 연결점 2 = DevLib 채널을 받는 컴포넌트. 이 둘은 **패키지가 아니라 Project_B 에** 둔다.

## 7. 정해진 것 한눈에 (바꾸려면 먼저 상의)

- MVVM, 위젯 이름은 Element.
- 값 상자는 같은 값 무시 · 구독 즉시 현재 값 (끌 수 있음) · 구독 길은 하나.
- 노출 규칙 (1.2 표).
- 파생 값으로 갱신 관계를 한 번만 선언.
- ViewModel 은 일반 C# · 기반에는 "구독 맡기기" 만 · 이벤트 시스템 도우미 없음.
- 위젯 묶기는 돌려주는 것 없음 · 위젯이 스스로 끊음 · View 가 ViewModel 정리 · 닫힌 화면은 정리 안 함.
- 위젯은 Reset 으로 컴포넌트 자동 채우기.
- 위젯 꺼내기는 생성된 partial 속성 (참조 배열 위) · enum 없음.
- 자동 연결은 완전히 같은 이름만 · ViewModel 선언은 생성 안 함 · 생성 시점 셋 (프리팹 저장 · 컴파일 뒤 · 버튼).
- ScreenManager 는 씬 컴포넌트 · 메서드만 · 팝업 스택 · 여러 개는 만들고 파괴로 시작.
- 트윈은 DOTween 을 직접 (감싸지 않음).
- 패키지는 Unity 6000.3 · DevLib 모름 · 연결점 둘.

## 8. 직접 정할 것 (정하면 ROADMAP "정한 세부" 에)

- 모든 메서드 · 매개변수 이름과 모양.
- 알림 도중 구독 변경 처리.
- 파생 값 인자 수 (1 · 2 · 3 으로 시작).
- 목록 알림 종류.
- LabelElement 에 정수 편의 묶기를 둘지.
- CooldownElement 모양, VisibleElement 페이드.
- 기본 소리 SO 를 채우는 법 · 잠김 소리 · 토글 · 슬라이더 소리.
- 생성 파일 이름 규칙 · 이름 다듬기 규칙 · 같은 이름 처리.
- 하위 namespace 나누기.
- 팝업을 열린 상태에서 또 열 때 · 닫는 중에 열 때.
